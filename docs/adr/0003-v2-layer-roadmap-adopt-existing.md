# ADR-0003: v2 (自動改善ループ) の層ロードマップと「既存採用」方針

- 状態: 採択 (2026-09-19)。L0〜L2 は実装済み、L3 以降は未着手
- 関連: README「評価契約」, ADR-0001, ADR-0002

## 背景

この repo の v1 責務は「シミュレーターをクラウドへ運んで実行し、証跡付きで結果を持ち帰る」(README)。
その先の構想として、エージェントが「設定を変えて実行 → score を見る → 次の一手を決める」ループを
自動で回す v2 がある。2026-08 に先行概念・OSS・MCP 仕様を調査した結果、次の 2 点が分かった。

1. LLM × 社会シミュレーションの主要 OSS は「ローカル / クラスタ + API キー」前提で、安価な計算資源上で
   実験系列を台帳と評価器つきで自律的に回す基盤は見当たらなかった (この repo の搬送層が埋める空白)
2. ループ側の部品 (探索・進化・durable 実行・agent harness・MCP) は成熟した既存実装がある。
   自作すべきなのは搬送層だけで、残りは借りる方が速く、正しい

## 決定

v2 は次の層で積む。**各層は下の層が完成してから着手し、既存実装の採用を第一候補にする。**

| 層 | 役割 | 状態 | 方針 |
|---|---|---|---|
| L0 搬送 | queue / runner / 名義解決 / バックオフ | 実装済み | 自作 (この repo の存在理由) |
| L1 台帳 | 追記 JSONL・自動再開 | 実装済み | 自作。重量級の durable 実行エンジンは採用しない |
| L2 評価 | `score` 契約 (`core/evaluator.py`) | 実装済み (停止条件のハード強制は未着手) | 規約が本体。採点できない実験はループに入れない |
| L3 ラチェット | ベスト score の保持・悪化の不受理 | 未着手 | 既存の ratchet 枠に score adapter を書けるか**適合実測してから**決める |
| L4 探索 | 次に試す設定の提案と早期打切り | 未着手 | 提案 (sampler) と打切り (pruner) を分離した既存の探索ライブラリを台帳に接続する |
| L5 MCP | どのエージェントからでも実験を投入できる窓口 | 未着手 | 公式 SDK で薄い façade (submit / status / cancel + 結果 resource)。実作業は L0〜L1 に委ねる |

設計原則 (先行事例の失敗知見から):

- **evaluator を先に書く**。機械採点できない実験はループに入れない
- **停止条件をモデルに委ねない**。反復上限・予算・進捗なし検出は実行層で強制する
- **試行回数を第一の希少資源として扱う**。「何回の実験で 1 改善を得たか」を台帳で測る
- **閾値の引き上げは自動、引き下げは人間承認のみ**
- 候補は自動採用しない。前提条件を実データで確認し、`candidate / adopted / hold / rejected` を区別する

## 結果

- README の責務は v1 (搬送) のまま据え置く。v2 に着手する PR で README の責務定義を同時に更新する
- L2 の評価契約が v1 と v2 の唯一の接続点。ここを変えると上の層すべてに波及する
- colab は成果物を回収しないため (ADR-0002)、ループの実行環境は当面 kaggle と local

## 却下した代替案

- **探索・進化ループの自作**: 既存実装に対する優位が無く、検証コストだけが増える
- **L3〜L5 を一括で作る**: 長期ホライズンの自律実験はまだ成功率が低いという実測がある。
  1 サイクルを小さく (1 ジョブ = 1 仮説 1 指標) 保ち、層ごとに実走で確かめる
